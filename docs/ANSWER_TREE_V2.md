# 文章观点树 V2：拆解与碰撞实现说明

当前版本：`answer-tree-v2.7-flat-frontier`（schema 仍为 `answer-tree-v2`）

## 目标

把单篇回答转换为一棵可追溯的观点树：

```text
唯一总观点
└─ 动态层数的中间分支
   └─ 可碰撞观点（用户可见树的叶子）
      └─ 支撑材料、条件和原文定位（默认隐藏）
```

用户看到从总观点到碰撞边界的完整观点骨架，不直接看到后台全部原子材料。信息边界保存在后台，不进入用户可见树。

结构图的每个可见节点都使用 `display_text`（建议 12～26 字、硬上限 32 字的完整短总结）；它不能是目录词或长句节选。点击节点后只展示完整 `statement` 和逐条原文依据。视觉精简不改变碰撞判断使用的完整语义。

## 核心约束

1. 每篇回答恰好有一个 `root`，它是全文综合观点，不强求对应单句原文。
2. `branch` 只负责组织，层数动态，不能成为叶子；**只含 1 个子节点的 `branch` 一律折叠**（见下）。
3. `collision` 必须是可见树的叶子，必须有逐字可定位的原文支撑。
4. `support` 永远隐藏在 `collision` 下面，不作为默认碰撞对象。
5. 所有可见叶子都是 `collision`；无原文依据的 `collision` 删除，由此产生的空 `branch` 同时删除。

## 一、可碰撞层级的唯一标准：信息密度

可碰撞层级**不是「第几层」，而是一条信息密度带**。

- 同一回答的不同分支允许在不同深度停下：一条分支可能第 1 层就到位，另一条要到第 3 层。
- 判断一个节点该不该停下，只看它承载的信息密度是否落在密度带内。
- 密度带是**绝对标准**，不随文章长短、段落多少、清单项数变化。因此不同回答产出的 collision 必须彼此可比。

### 密度带的量化定义（`schema_validator.py`）

| 编号 | 判据 | 阈值 |
|---|---|---|
| D1 | 争议轴数量 | 恰好 1 个可被理性反对的核心判断 |
| D2 | 语义槽位 | 2～3 个（适用条件 / 核心判断 / 关键理由） |
| D3 | 字数 | 目标 40～75，硬边界 32～95 |
| D4 | 支撑材料 | 1～2 条，均可逐字定位 |
| D5 | 同回答横向一致 | 字数极差 ≤30，最长 ≤最短的 2 倍 |
| D6 | 可反对性 | 能指出作者排除了什么（见 `excludes`） |

密度画像逐节点写入 `node.density`，横向统计写入 `report.stats.density`。

**越界处理分两级**：
- 超过硬上限 95 字 → 几乎一定是一个节点塞了多个争议轴，直接判失配丢弃；
- 其余偏差 → 只记录在 `report.fixed`，不丢节点。

**重试收紧**：单篇结构图生成实测约四分钟，一次重试代价很高。只有**严重失配**才触发重试（极差 >45 字、比值 >2.6、或多于一个多句话节点，见 `density.severe`）。轻微偏离目标带不触发。

### 单子分支折叠（v2.7）

密度带决定「一个观点该不该停下」，但**层级本身也会向用户传达信息**：看到一个 branch，用户就会认为下面还有需要展开的东西。

实测问题：一个已经落在密度带内的观点被单独包了一层 branch，用户以为它还需要继续往下拆。根因在旧 prompt 的一条规则——「每个 branch 默认收敛为 1 个 collision」。它本意是「同一争议轴别拆成多条」，但字面读起来变成「每个 collision 都该套一层 branch」。

现在的规则：**`branch` 存在的唯一理由是组织 2 个或更多并列子节点。** 只有一个子节点的 branch 没有在组织任何东西，纯属噪声。

两道防线：

1. **prompt 侧**：明确禁止输出只含 1 个 collision 的 branch，并在内部审核清单里加了「自底向上扫每个 branch 的子节点个数」。
2. **校验侧兜底**：`_collapse_redundant_branches()` 在 `normalize_item` **之前**对模型原始输出做自底向上折叠：
   - `branch(唯一子节点是 collision)` → 该 collision 取代 branch；
   - `branch(唯一子节点是 branch)` → 内层取代外层（内层更具体）；
   - 链式单子结构一路折平；`root` 永不折叠。

放在规整之前折叠是关键：这样 `ancestor_path`、`group_id`、`collision_depths` 都按折叠后的真实结构自然算对，不需要事后修补。折叠动作记录在 `report.fixed`。

结果是同一篇回答里，可碰撞节点各自停在它真正该停的深度——第 1 层就到位的观点直接挂在 root 下，需要归类的才进 branch。这正是「可碰撞层级由密度决定，不由物理层数决定」在树形上的体现。

### statement 的写法

`statement` 就是节点代表的观点本身，不是标题也不是摘要：

- 作者视角第一人称立场，不写「作者认为」这类第三人称转述；
- 没有标题前缀，不写「核心观点：……」；
- 只有一句话，句中不出现句号、分号、序号；
- 40～75 字说清「谁 / 什么情况下 → 我的判断 → 一个关键理由」。

清洗规则：`_TITLE_PREFIX`（标题前缀）、`_REPORT_FRAME`（转述框架）、`_LIST_MARKER`（列表编号）在校验阶段自动剥离。

## 二、collision 的结构化语义字段

这些字段是碰撞判定的输入，由抽取阶段一次产出（有全文上下文时提取最便宜、最忠实）。

### 硬核心四项

| 字段 | 含义 | 缺失处理 |
|---|---|---|
| `axis` | 争议对象：这个观点在裁决的那件具体事，8～20 字 | 留空，降级为词重叠匹配 |
| `stance` | 主张方向：`should` / `should_not` / `conditional` / `descriptive` | 按表述特征推断兜底 |
| `conditions` | 适用条件，拆为 `audience` / `stage` / `premise` | 空数组表示普遍适用 |
| `excludes` | 作者明确排除或劝阻的替代做法，0～2 条 | 无原文排除表述则丢弃该条 |

### 选配三项

`strength`（absolute / conditional / tendency）、`tradeoff`（作者承认的代价）、`not_applicable`（声明的不适用范围）。有则用，缺则不阻塞。

### 两个关键设计

**1. 字段缺失降级，不丢节点。** 单篇生成约四分钟，丢节点会触发整树重试，代价远大于一个字段留空。下游 `pair_screen` 对空字段有兜底路径。

**2. `excludes` 取代了旧的 `_counter`。** 旧字段要求模型虚构「一句可能有人反对的意见」，产出质量全看运气，且容易造出原文不涉及的对立面；更严重的是它在 `strip_internal` 之后实际取到的永远是 `None`，属于死字段。新字段要求原文出现过排除表述（「不建议」「不要」「而不是」「与其…不如」等）才可信，可核对，且是判定真冲突的最强信号——**一方的主张落在另一方的排除项里**。

### 跨回答对象对齐

`axis` 措辞对不齐，结构化就会在碰撞时退化成模糊匹配。因此：

`server.mjs` 的 `knownAxesFor()` 把同一问题下已有 map 的 `axis` 清单作为 `knownAxes` 传给抽取服务，prompt 要求命中时**逐字复用**，确实是新对象才另起一个。

## 三、碰撞判定：三层闸门

### 为什么不做「综合分歧度打分」

**差异量 ≠ 冲突性。** 两个观点可以处处不同却毫无冲突，也可以只差一个字就直接对立。

真实误判案例（现在的回归基准）：

| 维度 | A | B | 差异 |
|---|---|---|---|
| 适用条件 | 30 岁职场人 | 有家庭、上有老下有小 | 大 |
| 角色 | conclusion（描述） | recommendation（建议） | 大 |
| 行动指向 | 创业 or 打工 | 不辞职、做副业 | 大 |
| 表述极性 | 正 | 负 | 大 |

四项全「大」，加权求和会打出高分。但真实关系是 B 把 A 那个分岔口**细化成了一个具体选项**，两者完全相容。按维度差异加总，恰好会放大这类误判。

**冲突是合取**：同一争议对象 ∧ 适用条件有重叠 ∧ 在重叠处两个主张不相容。三者缺一不可，与其他维度差异多大无关。

### 第 1 层：结构校验

`collision-core.js` 的 `validatePair`（前端）+ `do_collide`（服务端）：是否两个 ref、是否不同回答、是否同一问题、节点是否存在、是否 collidable。

语义判定**不在前端做**。原先 `collision-core.js` 里的 `evaluateCollision` 词重叠规则从未被调用，只有测试在跑，造成「前端有语义闸门」的错觉，已删除。

### 第 2 层：零 LLM 预检（`pair_screen.py`）

按必要条件逐项检查，任一不满足直接返回 `no_result`，**省掉一次模型调用**并给出可解释理由：

| 检查 | 不通过时的 code | 用户看到的理由 |
|---|---|---|
| C1 争议对象对齐 | `axis_mismatch` | 这两个观点在裁决的不是同一件事 |
| C2 适用条件有重叠 | `conditions_exclusive` | 这两个观点面向的不是同一类人 |
| C3 主张方向可冲突 | `stance_incomparable` | 一方只在描述现象，另一方在主张该不该做 |
| C5 观点不高度相似 | `claims_too_similar` | 这两个观点说的其实是同一件事 |
| C4 至少一个分歧信号 | `no_conflict_signal` | 在谈同一件事，但找不到任何实质分歧的迹象 |

**C4 是 v4 新增的正面要求，也是这次收紧的主体。** 旧版只有否证闸门：只要没被 C1～C3 拦下就放行，等于默认「分歧存在」。而「两人在同一话题下各说一面」是最常见的情形，绝大多数并无分歧。现在要求分歧必须留下**客观可核**的痕迹，至少命中一个：

| 信号 | 含义 |
|---|---|
| `excludes_cross` | 一方的主张落在另一方原文明确排除的做法里（最强证据） |
| `stance_opposed` | 一方主张该做、另一方主张不该做 |
| `same_axis_divergent_claims` | 同一争议对象下两个主张说法差异明显 |
| `absolute_vs_conditional` | 一方给绝对判断，另一方认为要看条件 |

阈值集中在文件顶部常量区（`AXIS_OVERLAP_MIN`、`CLAIM_SIMILARITY_MAX`、`DIVERGENCE_SIMILARITY_MAX` 等），调整通过率只改那里。

两个容易踩的坑，改阈值前先读：

- **`DIVERGENCE_SIMILARITY_MAX` 不能调太低。** 中文短句共享句式框架（「我认为选专业该优先看…」）本身会抬高相似度，阈值过严会把「同轴不同答案」这类真分歧误杀。实测 0.34 就会拦掉「优先看转身空间」× 「优先看起薪」。
- **`axis` 缺失走 fallback 时不能直接禁用 `same_axis_divergent_claims`。** 那会误杀真分歧。正确做法是提高共享词门槛（`DIVERGENCE_FALLBACK_SHARED_MIN`），而不是一刀切。「共享词多 + 相似度中低」恰恰是真分歧的特征；「各说一面」的配对共享词很少，在 C1 就被拦掉了。

**C2 只是否证闸门，不能反向当分歧证据。** 模型经常漏填 `conditions`，「双方都为空」不代表有分歧。`render_screen` 会在这种情况下明确提示模型「条件分歧缺少结构化依据」。

C3 的相容性查表关键项：`descriptive × should` 和 `descriptive × should_not` 一律判不可冲突——这正是上面那个误判案例被拦下的地方。`descriptive × descriptive` 保持放行（可能存在归因或机制冲突）。

`excludes` 交叉命中是**加分信号**而非必要条件，命中时 code 为 `direct_conflict_candidate`。

### 第 3 层：两步模型判定（`collide_engine.py`）

**拆两步的原因**：旧版一次调用同时要求「判断关系 + 写出问题 + 给出 evidence」，模型一旦开口就已预设关系成立，`无有效关系` 形同虚设。

**第一步只判关系。** 声称冲突类关系（归因冲突 / 机制冲突 / 直接对立 / 元层冲突 / 条件分歧）必须同时给出三项举证：

- `shared_axis`：两人共同裁决的那个对象（≥6 字）；
- `overlap_case`：一个同时落入双方适用范围的具体情形（≥12 字）；
- `incompatible_because`：在该情形下为何两个结论不能同时接受（≥20 字）。

任一项写不出来即判 `no_result`。这条规则命中上述案例：模型必须写出「一个既在 30 岁分岔口、又有家庭负担、且两人建议冲突的具体人」——写不出来，因为 B 是 A 那个分岔口的一个具体解法。

**v4 收紧了四处。** 这一层原先只有「三项非空」和「拦 superficial」两道实质闸门，是通过率过高的主要来源：

| 问题 | 现在的处理 |
|---|---|
| **`共识支撑` 绕过全部实质闸门**（真逻辑漏洞）：它既不在 `NON_PRODUCTIVE` 也不在 `CONFLICT_TYPES` 里，于是既不走 `no_result`、也不需举证，直接 `published`——而它的定义恰恰是「表面像分歧，实则共享同一判断」 | 并入 `NON_PRODUCTIVE` |
| 举证**只校验非空**，模型写「这个人」「不能同时接受」也算过关 | 加最小长度 + 笼统措辞黑名单 `_VAGUE_EVIDENCE`，复述要求不算举证 |
| **单条依据**即可声称对立 | 冲突类要求 `evidence ≥2` 条，双方各出一条 |
| 模型自述**无人交叉核对** | 判「直接对立」必须与预检的客观信号对得上（`excludes_cross` 或 `stance_opposed`），核不上即退回 |

阈值集中在 `collide_engine.py` 顶部常量区。

**分歧强度改用白名单。** 只有明确填写 `dispute_scale=substantive` 才继续产出问题；填 `superficial`、留空或填非法值一律 `no_result`。旧版只拦 `superficial`，漏填就直接放行。

新增关系类别 **`互补细化`**（一方是另一方在更窄条件下的具体做法），专门吸走这类被误塞进 `条件分歧` 的配对。它与 `无有效关系` 同属不产出问题的合法结果。

`共识支撑` 也在此列（v4 修正），它同属不产出问题的合法结果。

**第二步才提问**，且必须落在已举证的 `overlap_case` 上。

`no_result` 不计为技术失败——有些节点对就是不值得碰。

## 四、缓存版本

判定口径变更时两个版本号都要推进，否则旧结果会被继续命中：

- `PROMPT_VERSION = 'answer-tree-v2.7-flat-frontier'` —— 结构图缓存；
- `COLLISION_VERSION = 'collision-v4-strict-gates'` —— 碰撞结果缓存。

只改碰撞判定口径时也必须推进 `COLLISION_VERSION`，否则同一对节点会继续命中旧判定的结果。

## 五、视觉区分

可碰撞与不可碰撞**只用视觉语言区分，节点上不出现文字标注**：

- 不可碰撞（root / branch）：圆角矩形 + 虚线描边 + 浅灰底，光标 `pointer`；
- 可碰撞（collision）：胶囊形 + 实线蓝色描边 + 白底 + 左侧蓝色圆点，光标 `grab` / `grabbing`；
- 拖到不可放置目标：`.drop-invalid` 红色描边即时反馈。

节点类型仅通过 `aria-label` 向读屏设备暴露。误拖拽时因浏览器不触发 `drop`，提示统一在 `dragend` 给出。

## 六、本地验收项

- 简单回答可以由 root 直接连接 collision。
- 复杂回答允许 root/branch/branch/collision。
- 同一篇回答可以出现深度不同的 collision 叶子，但必须落在同一密度带上。
- **没有任何 branch 只含 1 个子节点**：已达到密度带的观点直接挂在 root 下，不被多套一层。
- 真正组织 2 个以上并列子节点的 branch 必须保留，折叠不能一刀切。
- 无原文依据的 collision 被删除；由此产生的空 branch 同时删除。
- 每个 collision 都带 `axis` / `stance` / `conditions`；`excludes` 无原文排除表述时为空。
- 前端能看到完整层级，只有末层观点可拖动碰撞；单击统一用于打开节点详情。
- 所有节点卡片只显示短观点；单击打开节点详情，双击定位网页原文，蓝色末层观点仍可拖拽碰撞。
- 浮窗标题与 root 卡片逐字使用同一个总观点 `display_text`；branch 也显示完整短总结，不显示内部目录 `title`。
- 不可碰撞的 root / branch 详情只展示原文依据；可碰撞 collision 详情展示「观点解释 + 原文依据」。
- 碰撞结果详情按「两位作者来源 → AI 分析 → 深入问题 + 问题具体说明 → 讨论」展示，回答下方展开的引申问题同样展示该说明。
- 支撑材料默认隐藏，展开后可以定位到回答原文。
- V1 缓存不会作为 V2 树展示。
- 描述性观点与规范性建议配对时被预检拦下，不消耗模型调用。
- 现有回答选择、浮窗最小化和碰撞入口不回归。
